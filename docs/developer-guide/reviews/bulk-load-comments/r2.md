## Findings

### F1 [introduced] A, the action forgets its press whenever the folder list refetches
A press that queues videos emits `files.updated` (`addons/media_import/backend/router.py:377`), which the core maps to the WebSocket event `drive.file_updated` (`backend/app/services/event_hooks.py:165`). The folder list refetches on it (`frontend/src/components/folder/useFolderFiles.ts:40` and `:386-396`: `reset()` empties the list), so `SelectionBar` is rendered with `selectedFiles` empty for a moment, `LoadCommentsAction`'s `selection` key becomes `""` and then the ids again, and its effect runs each time (`addons/media_import/frontend/LoadCommentsAction.tsx:30-34`): `press.current += 1; setState(idle)`. Consequences, all after a press and with the selection unchanged:
- the status line is cleared and the button is enabled again, which is the invariant "After a press the button cannot send another request until the selection changes";
- a response that arrives after the reset is dropped (`mine !== press.current`), so a slow answer shows nothing at all;
- every video that finishes loading emits `files.updated` too (`service.py:1181`, `:1214`), so while the queue runs the status never stays on screen for more than a few seconds.
Reproduced in the app (selection of three videos that already have comments, "Nothing to load"): press, status shows and the button is disabled; `window.dispatchEvent(new Event("loft-move-complete"))` (the list's own refresh trigger) and 1.2 s later the status is gone, the button enabled, and "3 selected" unchanged. Without my event the same thing happened on its own about 5 s after the press, because the folder refetches every 6 s on this install (the network log shows `/folders` and `/files?page=1` fetched about every 6 s, which would be a `drive.file_updated` from some other job; the cause was not identified). The N > 0 path is by reading (the code above), not pressed: pressing it on non-green videos was not allowed.
Not caught by tests because every test passes a stable `files` array. A fix would key the reset on the ids only while they are non-empty, or on what the user selected, not on what the list currently holds.
Reproduction against the parent: the effect and the state machine are in a file this branch creates, `[introduced]` without one.

Same cause, one more symptom: while the list is refetching, `selectedFiles` is empty but "3 selected" still shows, and a press in that window sends no request and answers "Nothing to load" (`LoadCommentsAction.tsx:38-42`, `ids.length === 0`). Seen at 375px: the list was a spinner and the bar still offered the action.

### F2 [introduced] B, the 990px threshold is a prediction that fails in states the bar really has
`LABEL_VISIBILITY = "hidden max-sm:inline @min-[990px]:inline"` (`SelectionBar.tsx`, near the end) says "names fit when the card is 990px". Measured in the deployed app (real Chrome, Windows, the app's own fonts), the room the nine named buttons need, and where it fails:
- **Tag editor open.** Pressing **Tag** replaces that button with an input, Apply and Cancel, 285px against about 90px. At a 1128px card (the widest the bar gets) the row ends at 1149 against a card edge of 1140 (Move to Trash clipped by 9px); at a viewport of 1100 it ends at 1149 against 1088, and Move to Trash is cut to "Move" in the screenshot; at 1014 it ends at 1149 against 1002, so the button is off the card. Names are still drawn at all of those widths. Without the addon button (about 144px) the same state fits at the wide end, so the addon makes it worse; the parent was clipped in this state at every width, so the state is not new. Also at a 640px viewport the icon-only bar with the editor open ends at 676 against 628.
- **Text size.** The threshold is in px and the buttons are in rem. With the browser's text size raised (root font-size set to 18px or 20px) the names still show at the same card widths and the row overflows: English at a 1030px viewport, root 18px, needs 1016 against a 1003px card (13px clipped); root 20px at 1030 and 1100 clips 113 and 43px. Japanese at 1152px, root 20px, needs 1201 against 1122 (79px clipped). `DESIGN.md` says thresholds in a container query are kept in `rem`. `EditorToolbar.tsx` uses px thresholds, so there is precedent; it does not meet the rule either.
- **Japanese has 17px of room**, not 72px: it needs 973px of the 990 (English 918). A system with a wider CJK fallback font would cross it. Not measured on another OS.
- **Another addon action.** Nothing bounds the number or the label length of offered actions; a second 150px action takes English to about 1070 and clips the end of the bar from 990 to 1070 (arithmetic from the measurements, not built).
Introduced: the threshold and the "fully visible at every width" invariant are this change's; a reproduction against the parent does not apply to a rule the parent did not have. By the letter of the revised invariant, "fully visible at every width from 640px up", the tag editor case is an A; the parent also clipped there, so I put it B, for the supervisor.

### F3 [introduced] B, the trash view lost its names
`LABEL_VISIBILITY` is applied by `ActionButton` to every bar, including the trash bar, which has two buttons (**Restore**, **Delete permanently**) and needs a few hundred px. Between 640 and 1013px those two are now icons with tooltips, and **Delete permanently**, the destructive one, has no visible name; before they were named at all widths. By reading the classes and the existing 375px test, not measured in the app: the trash is empty on this install, so I could not select anything there.

### F4 [introduced] B, icon-only buttons are 39px wide on a touch screen, and a tooltip cannot be read there
With `pointer: coarse` (the pane's mobile emulation, 700px viewport) the nine icon-only buttons measure 39 x 44. `DESIGN.md` says every button reaches a 44px touch target on a coarse pointer and that along a row the boxes are grown. The row has room (card 676px, buttons end at 430). Separately, `title` is the only place the name now exists between 640 and 1013px, which on a tablet in portrait (no hover) is not reachable; the `…` menu has the names only below 640. The user chose icons with tooltips, so I record the touch consequence rather than dispute the choice.

### F5 [introduced] B, the user guide does not say the bar's names become icons
`docs/user-guide/file-browsing.md` ("Selecting several files") lists the bar's actions and says nothing about names turning into icons with tooltips below about 1000px, or about an addon's actions. Only `docs/addons/media-import.md` says it, for **Load comments**. The rule in `CLAUDE.md` is that behaviour a viewer would take for broken gets a sentence in the user guide; a bar of unlabelled icons on a window that is not narrow qualifies.

### F6 [introduced] B, test gap: the label can carry the result again
Mutation `status-label-result` (`label: status ?? t("load")` in `LoadCommentsAction.tsx`), want=kill, LIVE. The revised invariant "An addon action's label does not change with its result" has no test that holds after a press: every post-press assertion is `toMatchObject({ status, disabled })` and `label` is asserted only in the idle states. This is the design that commit `83f701a` replaced. By R-4 a test that lets an A through is an A; the invariant here is the declared one, so the supervisor may bucket it A.

### F7 [introduced] B, test gap: two statuses
Mutations `join-comma` (`statuses.join(", ")`) and `status-first-only` (`statuses[0]`) both LIVE; want=live for the separator and want=kill for dropping the second status. Only one status is ever offered in a test. Not reachable with one action.

### F8 [pre-existing] B, the core actions' `displayLabel` is unpinned
Mutation `no-displayLabel-core` (`{action.label}` for the visible text) LIVE: nothing asserts that **Tag**, **Collection** and **Export** are the short texts. The round 1 assertion that covered it was for the addon's own `displayLabel`, which the redesign removed. The core `displayLabel` fields predate this branch.

### F9 [introduced] B, low, a live region inserted with its text
The status `<p role="status">` is mounted at the moment its text is set and removed when it clears. Screen readers announce a live region reliably only when the region already exists and its content changes. Reading only; no screen reader was run.
