## Findings

### F1 [introduced] B, needs the R-5 browser check; A if it holds
At `sm` and above every action is drawn on the bar, in a card that is `overflow-hidden` with `shrink-0` buttons. The addon adds a button of about 150 px, and its result label ("Loading started (1000)") about 190 px, to a row that has almost no slack. Measured on a static replica of the row (same class values, system font stack, Chrome; not the app): needed width 762 px without the addon, 918 px with "Load comments", 959 px with "Loading started (1000)"; the card at `max-w-3xl` is 744 px. If the real bar behaves the same, Move and Move to Trash are clipped on every viewport from 640 px up, and the bar jumps when the label changes under the pointer. Check the real app at 640 to 1000 px, en and ja, with the addon on. Not verified: the replica already overflows by 18 px with no addon, so its absolute numbers are off; the +150 to +190 px delta is the point.
`frontend/src/components/SelectionBar.tsx:246-254`, `addons/media_import/frontend/LoadCommentsAction.tsx:69-77`.

### F2 [introduced] B, design consequence to raise
The result is the button's label (spec decision) and an addon action is never on the bar on a narrow screen (invariant). On a narrow screen the action is a row in the `...` menu, and pressing it runs `closeMore()` first (`SelectionBar.tsx:318-321`), so the viewer sees nothing happen; "Loading started (N)" is visible only after reopening the menu. `docs/addons/media-import.md` says the button shows "Loading started (N)" and that on a narrow screen it is under the `...` button, which together imply feedback that is not there. Either accept it and say so in the doc, or let an action keep the menu open; the supervisor's call.

### F5 [introduced] B, the new query and the `except` are redundant, and nothing says which layer holds
`enqueue_missing_comments` filters by drive, active state, mime and URL support, then calls `enqueue_comments`, whose `_load_comments_item` repeats the drive, active, mime and `supports_comments` checks and raises `FileNotFoundError` or `ValueError`. Mutations removing each of `File.drive`, `active_file_filter()`, `File.mime_type`, `supports_comments` in the new code, and the `FileNotFoundError` / `ValueError` catches, all survive (live x6; `catch-removed` and `catch-value-removed` were want=kill). So the drive-boundary and trash invariants are held by the reused function; the new query is a prefilter. The catches are not dead: a threadpool handler (trash, scanner) can change a row between the read and `_load_comments_item`, but no test makes that happen. Decide whether to keep the prefilter as an optimisation, and if so pin the catch with one test that makes `_load_comments_item` raise. `addons/media_import/backend/service.py:786-824`.

### F6 [introduced] B, synchronous DB work on the event loop
`enqueue_missing_comments` is `async` but does its queries and up to N `_load_comments_item` calls (two queries and a session each) with no suspension point, so the loop is blocked for the whole call. In the test DB, 1000 candidates took 0.68 s (measurement, for the PR body, not the code). The single-file refresh does the same for one file; 1000 makes it visible to a viewer streaming at the same time. The same absence of a suspension point is what makes concurrent presses safe (no interleaving between `comments_pending` and the insert), so moving this to an executor would need a lock. I looked for a race with the worker and with a second press and found none: a fetching item is `comments_pending`, a finished one has `comments_fetched_at` set.

### F7 [introduced] B, partial queue on an unexpected error (by reading, not reproduced)
`enqueue_comments` is guarded only for `FileNotFoundError` and `ValueError`. Any other exception from `_load_comments_item` (for example `sqlite3.OperationalError`) in the middle of the loop returns 500 after earlier ids were queued, and `files.updated` is not emitted for them, so their icons stay grey while they load. A retry skips them as already queued and reports "Nothing to load". Low.

### F8 [introduced] B, intentional per spec, noted
A first fetch that failed with a permanent kind (`disabled`, `permanent`) has `comments_fetched_at` NULL, so every press queues it again and re-runs yt-dlp, and "Loading started (N)" never settles to "Nothing to load" for a selection holding one. The spec's decision is that a failed first fetch is queued; flagging the permanent kinds only.

### F9 [introduced] B, low
If chunk 1 of a selection over 1000 succeeds and chunk 2 rejects, the label is "Couldn't start" although up to 1000 videos were queued and `files.updated` went out. The retry then reports only the second chunk's count.

### F10 [introduced] B, low, not reachable with one bar
`selectionActions.ts` keeps "the first mount of an id" as the first entry of the inner `Map`. A republish of that mount (label change) runs `withdraw` then `offer`, which re-inserts it at the end, so the other mount's stale action then wins. Mutation `sa-last-wins` is live: no test pins which mount wins. Unreachable today because only one selection bar mounts one slot.
