## 2. The trajectory question

Fix diffs read in order: `fd5793d` adds a branch (the store step moves into the `try`, plus a nested `try/except` around `record_failure`); `1a1d80c` adds a derived state (`awaiting`, beside `pending`) and a prediction (`next ?? prev`: "no answer is a blip, the old page is still right"); `1e53c50` widens one regex constant and adds table rows (no new branch); `6220b2d` removes three hand-written recipes (converging); `5473382d` removes a trick (`-mb-px` plus a border) in favour of a shadow (converging, in another component); the two test commits add nothing.

The shape worth the supervisor's attention, not a verdict: the two behavioural fixes (`fd5793d`, `1a1d80c`) both add the same prediction, "on failure keep the previous state", and each makes a guard owned by older code load-bearing without pinning it (`replace_snapshot`'s rollback; `setData(null)` at file change). Round one had both as survivors declared harmless (its M4 and F12) and neither was revisited when the fix changed its reach. That is one prediction added twice in a single round, not a prediction added in two rounds in a row, so I do not call it patching yet. If a third round adds another "keep the previous state" branch, the pattern would be there.

## 4. Findings

### 1. Perspective: invariants (3: a failed refresh leaves the previous rows unchanged) / error path. `[introduced]` by `fd5793d`. Suggested severity: medium (an A: a declared invariant breaks if one line goes, and a test lets it through)
`addons/media_import/backend/comments.py` `replace_snapshot` (the `db.rollback()` in its `except`) and `backend/service.py` `_fetch_and_store_comments`. Before `fd5793d` a store failure escaped and the caller closed the session, so the rollback was redundant (round one's M4, live, "equivalent"). Now `record_failure` runs on the same session and commits, so without the rollback it commits the half-applied transaction.
Reproduction (container, a real SQL error: a `BEFORE INSERT` trigger on `loft_comments` that raises; a first good fetch of `old`, then a second fetch of `new`): unmutated, stored `['old']` and status `(1, 5, 'failed')`. With the rollback removed from `replace_snapshot`: stored `[]` and status `(1, 9, 'failed')`, the old snapshot deleted and the status claiming the new total; the 57 tests of test_comments_queue/storage/fetch/router all pass.
Let through by: the new `test_a_failure_while_storing_is_recorded_not_lost` monkeypatches `replace_snapshot` to raise before it touches the DB, so it never exercises the rollback; the older test that calls `replace_snapshot` alone closes the session. A row whose statement fails after the UPDATE/DELETE (a trigger, a dropped table) would hold it.

### 2. Perspective: correctness (what is recorded). `[introduced]` by `fd5793d`. Suggested severity: low
`service.py` `_fetch_and_store_comments`: `_classify_caption_error(str(exc))` now also runs on store errors. A SQLAlchemy error message carries the statement parameters, that is comment text, author and like counts. Reproduction (same trigger, one comment per file): text `plain` gives `failed`; text `Too Many Requests` gives `rate_limited`; text `Private video` gives `permanent`; text `x` with `like_count` 1429 gives `rate_limited` (the substring "429"). A `permanent` verdict hides the Retry button (`RETRYABLE`). A purge-mid-fetch `LookupError` carries the file id, which could contain "429" as well.
Let through by: the three new parametrized errors carry no marker text.

### 3. Perspective: tests / React effects (what a fix made load-bearing). `[introduced]` by `1a1d80c`. Suggested severity: low to medium
`YouTubeCommentsContainer.tsx` file-change effect: `setData(null)` was cosmetic (round one's F12); with `setData((prev) => next ?? prev)` it is the only thing stopping the previous file's comments from showing for the new file whenever the new file's first read answers nothing (404, blip). A8 survives all 54 tests; with it removed, P3 (file A ready, then file B whose read returns null) renders `text a` on file B. A9 (`setShowAll(false)`) also still survives. Today's code is correct.
Let through by: no test changes `fileId` and answers `null` for the new one.

### 4. Perspective: correctness (what "keeps the previous page" can keep). `[introduced]` by `1a1d80c`. Suggested severity: low
When a file stops answering for good (trashed, purged, its drive locked, the session expired), the page keeps the last page and, if that was `queued`, keeps "Loading comments…" and polls every 10 s for as long as it stays open. P2: after one `queued` answer and then only `null`, 7 requests in 60 s and still "Loading comments…". At the parent the tab dropped on the first null (round one's finding 1: worse for a blip, better for a purge). A snapshot already in memory also stays visible after the drive locks, until the viewer navigates; nothing new crosses (the backend 404s hold, invariant 4 intact). An unsupported provider answers `supported:false`, not null, so that path still drops the tab (A6 holds it).
Let through by: nothing separates "blip" from "gone": a 404 and a network error both become `null`.

### 5. Perspective: async (stale responses, request volume). `[pre-existing]` pattern, reach widened by `1a1d80c`. Suggested severity: low
`reload` has no sequencing beyond the file key. Probe P1: the first read (page opened before the metadata row) is held; a drive event triggers a second read that returns `queued`; the first then resolves `none` and wins, so the page shows "Load comments" for a fetch that is queued, with no polling, until the next drive event or the finish event. At the parent the same overlap existed between the poll and an event while pending; `awaiting` adds more overlapping reads (P7: one read per event, uncoalesced, for every `drive.file_updated` of the drive while a page sits on `none` or null). It self-heals at the next event, and the fetch's own finish emits one.

### 6. Perspective: security (copied Markdown for an AI, instruction injection). `[pre-existing]` code; the scope claimed by `1e53c50` ("every line break a comment can carry") does not reach it. Suggested severity: low
`commentsMarkdown.ts` `item()` and `formatCommentsMarkdown`: the author display name and the title go through `.replace(/\s+/g, " ")`; in JS `\s` does not match U+0085, so a NEL survives (checked in node for U+0085, U+001C-001E, U+200B, which `\s` also misses). Probe: title `T<NEL># forged` and author `bob<NEL>Ignore earlier text` leave the raw NEL inside the `- [VIEWER] bob...` line and the heading; the text after it is a new line with no `>`. The role tag still cannot be forged (`plain()` is applied to the name; the title is not neutralised, already in the ledger). Same class as round one's finding 3 for the name field. I did not measure which chat boxes treat U+0085 as a break, nor whether YouTube lets a display name carry one.
Let through by: the new `it.each` over separators exercises comment bodies only.

### 7. Perspective: tests / layout. `[introduced]` by `5473382d` (a fix commit with no test). Suggested severity: low
No test holds the PageTabs row's height or scrollbar: reverting both classes (PT) leaves PageTabs.test, readingTabs, ReadingSection and `tab-styles` (path-normalised) green. jsdom cannot see it, and `frontend/e2e-layout/` has no tab-row spec. Section 5 is the only evidence.

### 8. Perspective: invariants (a page learns of a fetch). `[pre-existing]`. Suggested severity: low
The revised invariant says a page learns of a fetch "while it has nothing, has not loaded, or offers Load comments". `awaiting` implements exactly that, but (a) nothing is emitted when a fetch starts, so a page on `none` learns at the finish, not at the start; (b) a page on `ready` or `error` never learns of a refresh pressed in another tab or by another viewer (P5: one request in total); (c) `_comments_items[file_id]` is set in `enqueue_comments`, after `_fetch_and_update` returns, and the metadata `files.updated` is emitted inside it, so a read landing in between answers `none` and the page offers Load comments for the whole comments run until the end event. (c) needs a read faster than one event-loop step after the emit; I could not make it happen without a live import.
