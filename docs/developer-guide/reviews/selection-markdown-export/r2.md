## Findings

### R2-1 [introduced] TOC anchor is computed from the heading's source text, and two common title shapes got worse than before the fix
- `frontend/src/components/markdownExport/document.ts:79` (`anchorOf`), used at `:145` on `e.heading` (`"N. " + oneLine(title)`); the heading is written as `## N. title`.
- A user hits: GitHub slugs the rendered heading, so markup that the Markdown consumes does not count. Titles that differ:
  - ends in a space and `#` (`C #`): `## 1. C #` renders as "1. C" (closing sequence), GitHub id `1-c`; export link `#1-c-`. At `9d7a8886`: `1-c`. Reproduction (same function copy-pasted at both commits): `"1. C #"` old `1-c`, new `1-c-`. [introduced] by this commit.
  - emphasis written with underscores (`_x_ y`): rendered text is "1. x y", GitHub id `1-x-y`; export link `#1-_x_-y`. At `9d7a8886`: `1-x-y`. [introduced] by this commit (`\p{Pc}` now keeps `_`).
  - `<b>x</b>`, `&amp;` give `1-bxb` / `1-q-amp-a` in both commits; GitHub slugs the rendered text. [pre-existing].
- Unverified (cannot run github-slugger here): `\p{N}` also keeps "other numbers" (`x²` gives `1-x²`, `½ cup` gives `1-½-cup`). From my memory of its generated regex, GitHub removes the Latin-1 superscripts and fractions. Not confirmed.
- Touches: "Every TOC link resolves to its own video's heading". The in-app dialog shows plain text, so only the pasted document is affected.

### R2-2 [introduced] Encoding brackets turns an IPv6-literal host into a different address
- `document.ts:93-95` (`linkOf`): `.replace(/\[/g, "%5B").replace(/\]/g, "%5D")` runs on the whole `href`, host included.
- Reproduction: `https://[::1]/x` becomes `https://%5B::1%5D/x`; `http://[::1]:80/` becomes `http://%5B::1%5D/`. Paths and queries with brackets (`?q=[1]`, `list=PL[1]`) become `%5B1%5D`, which servers treat the same. Ordinary YouTube/Vimeo/youtu.be addresses are unaffected (run: `https://youtu.be/abc?t=1`, `watch?v=abc&list=PL[1]`).
- Impact is narrow (an IPv6-literal video URL in a `.loft`); the declared invariant ("brackets encoded") allows it, so I report it as a consequence, not a violation.
- Also within the same function, not a structure problem: the whole metadata line is wrapped in `_..._`, so a link ending in `_` (`https://x/_`) writes `.../__`, and `*bold*` in a path is unescaped; both can render oddly in a Markdown viewer. Display only, no line is forged.
- Touches: "The original link … is a one-line http(s) address with its brackets encoded, or absent".

### R2-3 [introduced] A section of only zero-width characters still counts as a section
- `document.ts:14-15` (`outcomeOf`): `!outcome.markdown.trim()`. JS `trim()` keeps U+200B, U+200D, U+2060, U+180E, U+200E, U+0085.
- Reproduction: `trim()` of each of those, in node, is non-empty. A provider answering `{kind:"section", markdown:"​"}` gives an included video with an empty-looking `### Transcript` and no warning. Same for a section that is only `####`.
- The provider contract says to answer `empty`, so this is a robustness limit of the same kind as F5, not a documented misuse. Touches: "A section whose text is empty counts as missing".

Only `gapNoProviders` reaches real text (via the Container test). `.claude/rules/tests.md` ("fails under a behaviour-preserving refactor is a change check that was kept").
